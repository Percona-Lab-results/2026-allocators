Setup: 20-hour HammerDB TPC-C runs at ~2400 MHz with a 150 GB buffer pool, /proc/pid/smaps sampled every 30 seconds (~700 snapshots per run).

  • Physical residency is essentially a tie: average RSS spans just a 0.4 GB band (jemallocs 162.93 GB, glibc 163.26, tcmalloc 163.33 — a 0.25 % spread). With ~92 % of RSS being the buffer pool, the allocators barely differ on resident memory at this workload; their differences live in virtual address space (see the maps report).
  • RSS is flat: growth over 20 hours is −0.04 to +0.06 GB in every run — no leak or creep. Swap stayed at 0; file-backed RSS is negligible (~23 MB); the referenced working set hovers around 159 GB (nearly the whole pool stays hot).
  • THP never materialized: AnonHugePages is 0 in all 8 runs, including the “thp” ones — the kernel was in madvise mode and nothing called MADV_HUGEPAGE, so the thp/nothp comparison in this dataset measures noise. (The suite harness was subsequently fixed to set THP via sysfs and abort if huge pages do not engage.)

Bottom line: a 150 GB buffer pool dominates residency so completely that allocator choice is invisible in RSS here; this dataset established that none of the allocators leaks, and that a valid THP comparison required fixing the harness — both addressed in the later allocator perf suites.
