Throughput by phase — 80 threads

Each phase runs 80 threads × 1,000,000 operations (80M ops total) over a 1M-key space. Writes are identical across allocators; the random-read phase, which is CPU- and allocation-bound once the dataset is cached, separates them sharply.

Single-threaded baseline — 1 thread, 1M operations

The suite’s default fillrandom run (4 runs per allocator; bars show the mean, the table has every run). At one thread there is no lock contention to win, so the allocators sit within ~4% of each other — the contrast with the 80-thread read numbers is the finding.

Footnote: the 10M-key attempt

A heavier configuration (--threads=80 --num=10000000, i.e. 800M ops per phase) was started first but exceeded the 2-hour execution window with only glibc partially done, so it is not comparative and is not charted. The glibc numbers it produced before being stopped: fillrandom 199,295 ops/sec (4,014 s, 22.0 MB/s) and readrandom 2,256,908 ops/sec (354 s, 249.7 MB/s); overwrite was interrupted at ~71%. Note the much lower write throughput at 10M keys — more compaction work — while random reads remained fast.
